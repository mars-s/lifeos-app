# Smart scheduling for LifeOS

> **Direction changed on 19 November 2026.** Avi chose Morgen's model over Motion-style scheduling of the whole calendar: "a smart block that lets me put down a block of time and fit tasks in there depending on priority and size … that way it doesn't mess with my calendar too much." LifeOS now builds **Smart Blocks** (see the next section, `CONTEXT.md` and `docs/data-model.md`). The ranking, engine and Google advice below still apply, scoped to one Smart Block at a time.

## Smart Blocks: what Morgen does and where LifeOS differs

What Morgen's own guides say, read on 19 November 2026:

- **A Frame is a calendar event that templates "when you want to work on which type of task".** Click a slot, choose Frame, name it for the kind of work. It repeats like any event (no repeat, daily, weekdays, weekly, monthly, yearly, or a custom rule), defaulting to weekdays. It can be busy or free to others, and lives on a chosen calendar. [How to use Frames](https://www.morgen.so/guides/how-to-use-frames)
- **A filter decides which tasks are eligible**: task integrations, lists, projects and tags, combinable across sources. Due dates and importance count without being in the filter. [How to use Frames](https://www.morgen.so/guides/how-to-use-frames)
- **The AI Planner chooses by importance, due dates, available time, estimates and the Frame's filter**, with a Priority Factor that discounts tasks long past their due date. Estimates come from the task, a `[30m]` tag or a default duration; an optional 20% padding counters the planning fallacy. Breaks are tuned with a slider; long tasks can split across Frames. [Plan your day](https://www.morgen.so/guides/plan-your-day-using-the-ai-planner)
- **What does not fit**: Frames full, a task longer than the Frame ("a 6-hour task will never fit into a 4-hour Frame"), filtered out, or busy events on another visible calendar overlapping the Frame. Time-sensitive tasks that missed out are listed. [Troubleshooting](https://www.morgen.so/guides/troubleshooting-the-ai-planner)
- **Preview and approval**: proposals pulse over Frames; Schedule all books them; Esc discards. Delete ("Ignore task") lets other tasks fill the space; dragging a task in reshuffles the rest; resizing changes its duration. Tasks are not embedded in Frames, so moving a Frame leaves its tasks. Rescheduling suggestions always wait for approval. [Plan your day](https://www.morgen.so/guides/plan-your-day-using-the-ai-planner) · [Rescheduling assistant](https://changelog.morgen.so/rescheduling-assistant-rsvp-inbox-more-308543)

| Morgen | LifeOS Smart Block | Why |
| --- | --- | --- |
| A Frame is an event on a chosen calendar | A Smart Block lives in LifeOS only, for now | Avi asked not to write to Google or Apple yet. The shape (series, skipped dates, detached occurrences) maps onto one recurring Google event later |
| Filter by integration, list, project, tag, size | Filter by Area, Project and Label | Those are LifeOS's containers. Size is not a filter: packing decides what fits |
| Importance from the task's own priority field | Area Priority, set once in the Feature's settings | LifeOS Tasks have no priority field; Avi ranks Areas instead |
| Priority Factor fades long-overdue tasks | Overdue stays most urgent | Avi trashes or reschedules a stale Task himself; a silent fade would hide a missed Deadline |
| Estimate, `[30m]` tag or default | Estimate, else Smart Estimate marked as a guess, else 30 minutes | Smart Estimates already exist; one source of duration |
| Optional 20% padding, a breaks slider | A fixed 5 minutes between Tasks inside the block | Simple and visible; padding can become a setting if Avi misses it |
| Splitting across Frames | Too long is skipped with a note | Splitting is a follow-up |
| AI Planner (a model) proposes | A deterministic engine, same inputs give the same fill | Previews answer within a frame and cost nothing; AI hints can join later through the capability router |
| Remove, drag in, resize, Schedule all, Esc | Leave out, put in first, drag to reorder, resize the window, Enter, Escape | The same verbs, plus one undo for the whole fill |
| Tasks are not embedded in a Frame | Fill Work Blocks are linked and pinned | A refill keeps them and frees only done, removed or ineligible Tasks |

Give Avi a weekly preview built by a small, deterministic scheduler. Let Area order decide between Tasks with room to spare. Give scarce time to work that will otherwise miss its Deadline. Keep accepted Work Blocks still unless there is a reason to move them. A new meeting can displace a flexible tennis session, but a court booking stays put. Show Avi the proposed move and its reason before writing anything. Publish accepted blocks to one Google-owned LifeOS calendar. Use AI only for optional hints about the work. The first version needs no model calls. [Research issue](https://github.com/mars-s/lifeos-app/issues/59)

## 2. Which scheduling engine fits?

Spread already snaps to five minutes, leaves ten minutes between blocks, and uses Day Plan order. Its cursor advances after each placement. A later short Task can therefore miss an earlier gap. The web preview includes busy time, Sleep Windows and existing blocks. The commit checks open Tasks and Work Block overlaps. Smart scheduling needs to recheck the other constraints at acceptance too. [Placement](../../packages/backend/shared/spread.ts) · [Preview inputs](../../apps/web/src/components/app/planner/spread.ts) · [Commit](../../packages/backend/convex/planner/workBlocks.ts)

| Approach | Fit for LifeOS |
| --- | --- |
| Scored placement into free intervals | Recommended. Try each eligible gap and preserve valid blocks on repair. Cheap enough to target interactive previews. A greedy choice can strand a long Task. Try one bounded swap before declaring that the proposed plan falls short. |
| Weighted interval scheduling | Useful when choosing between known candidate intervals. The ordinary formulation cannot express “place this Task once across seven possible days” or link its chunks without additional constraints. |
| CP-SAT or mixed-integer linear programming | CP-SAT can model optional intervals, no overlap and precedence. A time-indexed MILP can choose starts with binary variables. Both can optimise missed deadlines and movement together. They need a solve budget and a feasible fallback. Try CP-SAT on the Home Server if examples show the heuristic misses feasible deadlines. [OR-Tools scheduling example](https://developers.google.com/optimization/scheduling/job_shop) |
| Local search | Start from the last valid plan. Try moves or swaps that improve the objective. Bound the neighbourhood and use stable tie-breaks. Useful for repair. A failed search cannot prove infeasibility. |
| Pure language model | A plausible list of timestamps gives no overlap or capacity guarantee. Every edit needs inference and full validation. A retry can change unrelated blocks. Poor fit for the placement loop. |
| Hybrid | Use the same deterministic engine with or without hints. Cache optional judgements about split suitability or energy. This adds interpretation without putting model latency, spend or availability on the preview path. |

### Proposed policy

1. **Choose eligible work.** Start with the Day Plan and Inbox Tasks Avi explicitly selects for scheduling. Include open Tasks whose When permits the proposed day. Keep Someday, completed work and future Recurrence Rule occurrences out. Schedule each generated occurrence once. Show an accepted Estimate first, then a labelled Smart Estimate or an editable default. Deduct minutes already covered by retained Work Blocks. Never change a Deadline by scheduling. [Domain definitions](../../CONTEXT.md)
2. **Build real gaps.** For seven local dates, intersect Working Hours with time after now. Subtract the union of busy External Commitments, Sleep Windows, active work and retained blocks. Respect included Calendars and existing free, declined and all-day rules. Reserve ten minutes between neighbouring commitments and work. Convert local boundaries to instants for each date so daylight saving changes work. Count splits towards the same Estimate. Default to one whole block. Allow explicit splitting with a proposed 25-minute minimum and 90-minute maximum, or one whole short Task. [Capacity and calendar policy](../data-model.md)
3. **Rank Tasks, then score slots.** Suggested starting weights, all inputs scaled from 0 to 1: `rank = 45 × urgency + 35 × area + 15 × committedToday + 5 × age`. Give unassigned Tasks a neutral Area value. Cap age at 30 eligible days. Derive urgency from remaining Estimate divided by eligible free minutes before Deadline, capped at 1. No Deadline gives zero. For competing Deadlines, walk the due dates in order. Compare cumulative minutes due with the usable time left. First reserve scarce feasible slots for Tasks that would otherwise miss their Deadline. Check contiguous fit as well as total minutes. Tie-break by Day Plan order, then stable Task ID.
4. **Respect the Goal.** Among feasible placements prefer days below Goal, Avi's chosen energy windows, then the earliest equally good gap. Prefer fewer splits. Compare candidate repairs first by deadline shortfall, then number of accepted blocks moved, then total displacement, then preference fit. Keep a feasible accepted block in place for a mere score change. A day above Goal needs explicit approval. Working Hours and Sleep Windows stay hard. Show a shortfall in minutes and the earliest alternative. Label a heuristic miss “couldn't find a fit”. Reserve “impossible” for a demonstrable bound, such as 90 minutes required with only 45 minutes free.
5. **Repair the affected area.** Recompute proposals on a changed busy interval, Task, Deadline, Area order, Goal or manual request. Coalesce bursts for a few seconds. Refresh at local day rollover. First move only the collided flexible block, then try one nearby swap. Freeze started blocks and the next 60 minutes. When a meeting hits a pin or the freeze window, surface the conflict and ask which block to change. The external meeting stays exactly where its organiser put it. Manual moves and resizes pin that Work Block until Avi releases it. A flexible tennis Task can shift. A tennis booking imported from a calendar stays fixed.

Run a pure TypeScript planner against the same snapshot on client and Core. Use Core to validate the accepted result in one short mutation. Convex currently allows one second of user code per query or mutation. Its native actions allow 30 minutes and 64 MiB, and Node actions allow ten minutes with 512 MiB by default. Keep network calls in actions. Use a leased Worker on the Home Server for any future native solver, returning a proposal tagged with its input revision. [Convex limits](https://docs.convex.dev/production/state/limits) · [LifeOS Worker model](../architecture.md)

## 3. Which AI, for which job?

**Decisions fits small judgements.** Send one Task and several named questions to `POST /v1/decisions` with `gpt-6-luna`. A predicate returns a probability. A choice returns probabilities over supplied alternatives. A score evaluates ordered rubric levels and can fall between levels. The reference allows 1 to 400 questions on the same input. It supplies no free-text rationale. [Decisions guide](https://developers.openai.com/api/docs/guides/decisions) · [Create reference](https://developers.openai.com/api/reference/resources/decisions/methods/create)

| Job | Proposed route |
| --- | --- |
| Estimate | Reuse the existing Smart Estimate and Avi's overrides. Avoid a second duration call. |
| Split or energy hint | Ask whether the work has independent parts. Offer a choice of deep work, light admin or unknown. Map that choice to Avi's preferred windows. Show uncertain answers as optional suggestions. |
| Importance or flexibility | A rubric can flag wording that suggests time sensitivity. A predicate can flag a possible booking. Only Avi sets Area order, authorises moving an appointment or releases a pin. Test hints against his corrections before giving them any weight. |
| Schedule and explain | Place blocks in code. Generate reasons from the actual constraint that changed. A text model can paraphrase a diff or turn “keep mornings for uni” into a schema-validated draft preference for approval. Reject unknown IDs or unsupported operations. |

**OpenCode Go is a coding-agent subscription.** Its docs expect typical coding-agent traffic, an identifiable client and a stable session ID. The API being callable does not establish that unattended planner calls fit that use. Use the incoming capability router. Leave Go off for scheduling unless OpenCode confirms this workload is supported. A standard metered text endpoint or a reason template can cover the explanation job. [Go client guidance](https://opencode.ai/docs/console/go/)

**Costs in USD, checked 19 November 2026.** A meeting-only replan needs zero model calls. Ten changed Tasks at 500 uncached input tokens each cost about **$0.0005** on Decisions at $0.10 per million input tokens. Decisions charges nothing for output. Cache by relevant Task fields, rubric, model and user overrides. Send only needed Task text when the Feature is enabled. [Decisions pricing](https://developers.openai.com/api/docs/guides/decisions)

## 4. Writing to Avi's Google calendar

**Prefer Google Calendar API from Core.** The Mac currently supplies External Commitments through EventKit while the app is open. Issue #43 proposes an EventKit writer and Apple authority over published timing. Adopt one writer for the dedicated calendar. Agree the authority change in #43 before implementation. Google would own the published event timing, and LifeOS would own Task fields, proposed times and scheduling policy. Apple Calendar can remain a synced view and the source for other commitments. [Current authority](../../CONTEXT.md) · [Issue #43](https://github.com/mars-s/lifeos-app/issues/43)

| Route | What can be relied on |
| --- | --- |
| EventKit on Mac | A new calendar can be assigned an EventKit source before its first save. That alone does not give the account permission to create it. Google explicitly omits CalDAV's MKCALENDAR operation. Provision the calendar in Google first if taking this route. Events in an existing writable synced Google calendar can travel through Apple Calendar. A successful local save gives no remote delivery receipt or delivery deadline. Test create, move, delete, sleep and reconnect on the actual Mac and iPhone before claiming reliability. [Apple source property](https://developer.apple.com/documentation/eventkit/ekcalendar/source) · [Google CalDAV support](https://developers.google.com/workspace/calendar/caldav/v2/guide) |
| Google API from Core | Authorise the intended Google user and call calendars.insert once with the name LifeOS and Avi's time zone. Google makes that user the owner. Store the returned calendar ID. The scope calendar.app.created permits creating secondary calendars and managing events on calendars created by this app. The watch endpoint accepts it. Other calendars continue arriving through the Mac mirror. No general calendar write scope is needed for this design. [Create calendar](https://developers.google.com/workspace/calendar/api/v3/reference/calendars/insert) · [Scope meanings](https://developers.google.com/workspace/calendar/api/auth) · [Watch scopes](https://developers.google.com/workspace/calendar/api/v3/reference/events/watch) |

**Consent.** Use a Personal-mode Cloud project created by the intended Google account. It admits only its creator, needs no verification and avoids the seven-day refresh-token expiry of External Testing. Personal mode is a one-time project choice. Use a web OAuth client, exact HTTPS redirect, one-time state and offline access. Store refresh credentials server-side outside Activity. Show the selected Google account during setup and require it to match the destination Avi named. No sign-in or live sync was performed for this research. [Google personal setup](https://support.google.com/cloud/answer/15544987) · [Audience and expiry](https://support.google.com/cloud/answer/15549945) · [Web OAuth](https://developers.google.com/identity/protocols/oauth2/web-server)

**Identity and edit rules.** Give each accepted Work Block one stable provider-valid event ID, scoped to the calendar. Add a private extended property with its LifeOS identity. Keep a local mapping and last acknowledged timing, revision and etag. On an ambiguous insert, fetch that ID before retrying. Never identify events by title. For a calendar-creation timeout with unknown outcome, reconcile the intended calendar before issuing a second create. [Event IDs and private properties](https://developers.google.com/workspace/calendar/api/v3/reference/events) · [Conditional writes](https://developers.google.com/workspace/calendar/api/guides/version-resources)

- **Google drag or resize.** If the remote timing differs from the last acknowledged write, import it as Avi's manual change and pin that block. A resize changes reserved minutes. Keep the Task Estimate. Ignore a matching write echo. For simultaneous edits, use If-Match, fetch on 412 and show both times before allowing an overwrite.
- **Google delete.** Remove the reservation, keep the Task and suppress automatic recreation until Avi chooses to schedule it again. Keep an event tombstone. Undo should enqueue an inverse calendar change only if the remote state still matches.
- **No duplicate busy time.** Bind the dedicated Google calendar to its EventKit calendar identity during setup. Exclude that calendar from the Mac busy mirror only after the Google reader covers it. Render mapped events as Work Blocks once. Treat an unrecognised event on that calendar as an External Commitment and leave it alone.
- **Observe changes.** Do an initial paginated events.list. Save nextSyncToken after the last page. Watch the calendar through HTTPS. Check channel token and resource identity. Notifications signal a change without its contents. Queue incremental sync, handle cancelled events and renew expiring channels. Poll periodically because notifications can drop. On 410 rebuild the remote mirror, keeping local Tasks, pending writes and pins. [Incremental sync](https://developers.google.com/workspace/calendar/api/guides/sync) · [Push delivery](https://developers.google.com/workspace/calendar/api/guides/push)
- **Operational limits.** New-project quotas are 10,000 requests/minute/project and 600/minute/user/project. Google also limits bursts against one calendar. Coalesce writes per block and retry rate limits with jittered exponential backoff. The Google watch covers this calendar only. A meeting created on another calendar may remain invisible until the Mac syncs. Show last sync time and flag a stale preview. If always-on meeting detection matters, scope a separate read-only calendar connection. [Calendar quotas](https://developers.google.com/workspace/calendar/api/guides/quota) · [Mac sync window](../architecture.md)

## 5. Preview before lock-in

Keep Spread's ghost blocks, Enter to place and one Undo. Keep an accepted block solid while its proposed replacement appears outlined. Give each change a text label so it is readable without colour or animation. Let Avi inspect the plan as inputs arrive. Preserve the selected block and scroll position during recalculation. Morgen's editable preview and Sunsama's change-specific undo are useful precedents. [Existing Planner](../../apps/web/src/components/app/screens/planner.tsx) · [Morgen preview](https://www.morgen.so/guides/plan-your-day-using-the-ai-planner) · [Sunsama undo](https://help.sunsama.com/docs/usage-guides/timeboxing/timeboxing-auto-scheduling/)

| What Avi sees | What he can do |
| --- | --- |
| **Tennis · moved from 14:00 to 16:10.** The 14:00 meeting uses its old slot. The new slot leaves ten minutes after the meeting. | Accept this move, choose another slot, or keep tennis pinned and review the collision. |
| **Essay · 45 minutes short before Friday.** The only remaining gap is 30 minutes. The Task needs 75 uninterrupted minutes. | Allow a split, release another block or edit the Deadline himself. |
| **Two moves, one new block, five unchanged.** Old and proposed times appear together. | Review only changes. Accept all with Enter, accept a selected group, or discard with Escape. |

Keep dependent changes together. If tennis can only use a slot vacated by another move, accept both or recompute a feasible alternative. Rejecting a proposal leaves the original plan intact. Revalidate pins, busy intervals, Goal and revisions on acceptance. If a meeting arrived during preview, refresh the affected diff before committing. One accepted group creates one Activity entry. Show Google delivery separately as pending, synced or needing attention. Undo the accepted group with the same concurrency checks and queue the corresponding remote changes.

## Architecture and phases

| Phase | Data, ownership and proof before moving on |
| --- | --- |
| 1. Local preview | Add an optional Smart Scheduling Feature to Planner. Store Area rank and scheduling preferences in Settings. Extend Work Blocks with scheduling origin and pin state. Treat legacy blocks without an origin as pinned. Reuse When, Estimate, Goal, Working Hours, Sleep Window and Recurrence Rule occurrences. Keep drafts ephemeral with an input revision and reason per change. Compare repeated previews of identical inputs. Verify stable order, no overlaps, DST, split totals and no writes on discard. [Existing tables](../data-model.md) · [Feature registry](../architecture.md) |
| 2. Accept and repair | One owner-guarded changeMutation validates the whole selected diff against current Core data and records it. Use a request ID for retry safety. Apply explicit When changes for selected Inbox Tasks in that same undo group, showing them in the preview. Exercise a last-minute meeting, conflicting pin, partial acceptance and stale preview. Measure p95 preview time, unnecessary moves and deadline shortfall on Avi-approved sample weeks. |
| 3. Google projection | Calendar module owns the private Google connection, calendar mapping, event links, sync cursor and watch expiry. Index links by Work Block and by calendar plus event ID. Atomically queue a revisioned write with each accepted change. An internal action handles OAuth, retries and receipts. Reconciliation compares current desired state after retries and undo. Show the block exactly once on web, Mac, iPhone and in Google. Prove a remote drag survives a retry and a dropped notification. Coordinate with #43. |
| 4. Optional AI and deeper search | Route scheduling hints through the planned per-capability AI provider. Cache the result and provenance. With AI off or unavailable, the same deterministic planner runs. Compare acceptance and correction rates with the baseline. Add a leased CP-SAT Worker only if recorded failures justify its cost. Replay those weeks with equal hard constraints and a fixed solve budget. |

## Open questions for Avi

1. Should Inbox scheduling start with your explicit selection, or may LifeOS propose from the whole Inbox? Should accepting a cross-day move also change the Task's When when it has blocks on several days?
2. Should University always beat Personal, or only when both have enough time? Can a Deadline justify exceeding the Goal after you approve it?
3. Is tennis usually solo practice or a booking with someone else? Are seven days ahead, ten-minute gaps and one hour of notice good defaults?
4. Should Google deletion leave a Task unscheduled until you choose it again? Should a published flexible block show as free to other people until its Deadline is at risk?
5. Is delayed detection while the Mac sleeps acceptable? If not, which Google calendars should Core be allowed to read for availability?
